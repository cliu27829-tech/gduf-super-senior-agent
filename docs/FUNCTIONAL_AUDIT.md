## API 与持久化审计

- 注册、登录、刷新、退出、个人资料、密码修改均由 FastAPI 和数据库实现，不是 `localStorage` 假登录；密码使用 Argon2，Token 使用 HttpOnly Cookie。
- 任务、提醒、对话和消息均已有数据库表并按 `user_id` 查询；不是 React state 或 Python 内存持久化。
- 本机开发默认数据库为 `data/gduf_web.db`。Docker Compose 已配置 PostgreSQL 16 和持久卷，但当前电脑没有 Docker/5432 运行态，不能把当前本机状态描述为 PostgreSQL 已运行。
- `POST /api/agent/chat`、对话列表/详情/删除接口已存在，但请求字段只有 `campus_id`，未兼容需求中的校区 slug `campus`。
- Agent 意图分类在配置 Key 时会请求 DeepSeek JSON并用 Pydantic 校验；未配置或失败后使用规则。但通用学习/生活/聊天回答没有调用生成模型，属于固定模板，不满足“真正 AI 对话”。
- 通知解析确认后确实写入 `tasks` 和 `task_reminders`；ICS 确实动态生成且已有两个 `VALARM`。不过通知结构字段不足，规则解析也不支持一条通知拆多任务。
- 地点、饭堂、来源 API 已实现，但生产接口没有统一排除 `demo_fixture`；数据状态值还混用 `historical_seed`、`unverified_seed`，不符合产品约定枚举。

## Mock 与静态数据审计

- 生产前端没有使用 `setTimeout` 模拟 AI，没有使用 `localStorage` 保存登录或任务，也没有静态 JSON 直接模拟用户数据库。
- `Mock` 只出现在 Vitest/pytest 测试中，这是正确用法。
- 首页在校区 API 失败时使用硬编码校区数组，属于应删除的故障掩盖。
- 校园公共种子数据来自 `data/campuses/`，属于允许的公共种子数据；其中 `demo_fixture` 当前会进入生产 API，必须过滤。
- 广州数据只有校区锚点、北苑/南苑饭堂、北教学楼；北教学楼为演示条目。清远有演示饭堂与敏学楼。现状无法可靠回答快递、医务室、校园卡补办等常见问题。

## 当前对话为什么“看起来能用、实际不好用”

1. 无模型配置时所有消息都走规则，而且前端只显示一个笼统降级提示。
2. 即使配置模型，模型目前只做意图分类，不负责普通回答；“高数跟不上”等问题仍返回固定建议。
3. 中文地点查询按整段长词做数据库 `contains`，例如“北教学楼在哪里”很可能无法命中“北教学楼”。
4. 饭堂问题的规则顺序会先命中 `canteen_search`，不一定进入餐品工具。
5. 工具结果没有统一 `data_status`，响应也缺顶层 `data_status`。
6. 请求失败后没有“重新发送”，历史也不能从页面删除。

## 三条最小闭环缺口

### 1. AI 对话与工具调用

- 缺真实通用生成回答和可 Mock 的模型网关。
- 缺可靠中文实体匹配、校区 slug 解析、结构化数据状态。
- 缺重试、删除历史、清晰的基础模式说明。

### 2. 通知转任务

- 缺提交对象、文件命名、注意事项等字段。
- 缺规则模式多任务拆分。
- 日期解析缺本周五、周五、两天内、三天后、月底等表达。
- 任务页缺原通知查看与完整字段编辑。

### 3. 地点与饭堂查询

- 生产 API 必须排除 `demo_fixture`。
- 需要把可公开核对的历史官方饭堂项目作为 `historical` 数据提供，同时明确不代表今日供应。
- 快递、医务室、校园卡等只能返回来源支持的范围；不知道精确楼栋时必须明确说明，不得猜测。

## 修复完成前的产品结论

当前版本具备全栈骨架和一部分真实数据库能力，但仍不能称为三个核心流程全部可用的 MVP。本轮将只围绕以上缺口修改，不增加新页面；完成标准以自动测试、正式构建、人工冒烟和持久化复登验证为准。
