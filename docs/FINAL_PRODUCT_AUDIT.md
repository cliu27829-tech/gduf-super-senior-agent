## 运行基线

- 前端 `127.0.0.1:5173`、后端 `127.0.0.1:8000` 可启动；`/health`、`/ready`、`/api/agent/status` 均返回 200。
- 后端使用 SQLite 本地数据库，不依赖 5432 端口；数据库就绪检查通过。
- DeepSeek 已配置，模型为 `deepseek-v4-flash`；健康接口未返回密钥。
- 高德 JS API 与安全代理已配置；后端 WebService Key 未配置，因此 POI 核验依赖浏览器 JS API 或管理员人工校准。
- 前端 typecheck、20 个 Vitest 用例和 build 通过；后端 compileall 与 60 个 pytest 用例通过。
- 现有 Playwright 共 5 个用例，其中 2 个通过、3 个因本机凭据/管理员门禁跳过。现有用例没有覆盖本轮真实通知和坐标质量标准。

## P0：比赛演示会直接失败

1. 通知服务先按编号切分，再把每段都变成任务；真实“正大杯”通知会把规则误当待办。
2. 无年份截止日期只以当前时间为锚点；过去日期会被推到下一年，与通知发布时间语义冲突。
3. 通知输出只有 `drafts`，缺少 `notice / rules / action_items / deadlines / warnings` 分层，也没有条件和证明材料字段。
4. 通知解析与日期服务包含损坏的中文常量；旧测试也使用损坏文本，未验证真实中文输入。
5. 数据库 13 个地点中有 GPS 坐标的地点为 0、可导航地点为 0；教学楼、饭堂、宿舍仍只有示意 `map_x/map_y`。
6. 管理后台只能手填经纬度，没有地图点击、拖动 Marker、卫星图、POI 搜索和坐标证据工作流。
7. 路线门禁只看“有坐标且不是待核验”，没有 `coordinate_accuracy` 质量等级。

## P1：体验明显不好

1. 普通用户导航与路由仍公开 `/knowledge/import`、`/knowledge/sources`，与最终产品方向冲突。
2. 地点详情暴露可信度百分比和内部状态枚举，不是学生易懂的坐标状态说明。
3. 饭堂虽然有关联 `location_id`，但现有正式饭堂均无 GPS；页面不能明确区分可导航与位置待核验。
4. 办事流程仅有“校园卡丢失挂失与补卡”1 条；报修、网络、图书馆流程没有可靠结构化数据。
5. 首页四个入口仍是 AI 对话、查校园、处理通知、我的任务，没有按“问大师兄 / 校园地图 / 通知转待办 / 校园生活”收敛。
6. Agent 通知工具虽然调用同一服务，但只返回任务数组，无法展示规则和任务分离结果。

## P2：可以后续优化

1. 后端测试必须使用仓库根目录虚拟环境；系统 Python 未安装项目依赖，运行说明应明确解释器路径。
2. 高德 WebService Key 缺失时，服务端不能直接做 POI 搜索；浏览器校准模式需承担本地核验入口。

## 数据与仓库审计

- `好人师兄/` 当前包含 4,641 个跟踪文件，工作树体积约 443.6 MB，混有公众号全文、图片、广告与商业推广。
- 当前数据库包含 251 份知识文档，其中大量为本机私有导入；本地数据库已被 `.gitignore` 排除，不在 Git 跟踪中。
- 原始资料删除前只抽取简短结构化线索到 `data/curated/`；非官方线索一律标记 `needs_verification`，不保留全文和广告。
- `.env`、`.env.local`、数据库、上传目录和 Playwright 产物已在忽略规则中；最终仍需执行密钥扫描和 `git diff --check`。

## 初始结论

现有页面和基础自动化能运行，但尚未达到“真实通知可用”和“真实校园坐标可用”的验收标准。修复顺序为：通知解析与日期锚点 → 坐标质量与校准 → 产品入口清理与精选内部知识 → Agent/办事/全站回归。
